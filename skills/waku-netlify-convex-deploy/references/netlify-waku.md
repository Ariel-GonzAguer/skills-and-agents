# Waku on Netlify

## Choose static or dynamic output

Pure static Waku deployments use the current Netlify adapter with `static: true` and publish `dist/public`. This removes the request-time Waku runtime. It is valid only when every route and API response can be generated at build time.

Dynamic deployments produce static assets plus server output and a Netlify Function. Current Waku-generated output has historically used:

```js
const { INTERNAL_runFetch } = await import("../dist/server/index.js");

export default async (request, context) =>
  INTERNAL_runFetch(process.env, request, { context });

export const config = {
  preferStatic: true,
  path: ["/", "/*", "/RSC/**/*"],
};
```

`INTERNAL_runFetch` and generated paths are internal/version-sensitive. Prefer output generated by the installed Waku adapter. If a checked-in wrapper is required, compare it with the current official adapter source before editing.

## Baseline configuration

Typical dynamic output requires these concepts, not necessarily this exact file:

```toml
[build]
  command = "pnpm build"
  publish = "dist/public"
  edge_functions = "netlify/edge-functions"

[build.environment]
  NODE_VERSION = "22"

[functions]
  directory = "netlify-functions"
```

If `netlify.toml` already exists, Waku may not merge or replace it. Audit it against generated output. Do not add `included_files = ["private/**"]` merely because older Firebase projects used it.

The Functions source directory must remain outside `dist/public`.

## Build and deploy commands

Current Waku documentation uses a Netlify build signal when building manually:

```bash
NETLIFY=1 pnpm build
pnpm exec netlify deploy
```

Netlify's hosted build environment already supplies platform context. Verify current Waku behavior before adding `NETLIFY=1` to cross-platform package scripts.

Netlify CLI draft deploys and production deploys are distinct. Inspect `pnpm exec netlify deploy --help` before invoking. Production normally uses `--prod`, but never infer production intent.

## Environment scopes and contexts

Netlify contexts include `production`, `deploy-preview`, `branch-deploy`, and `dev`. Values can differ by context and scope.

- Convex deployment keys are build-time secrets: Builds scope.
- Netlify Function runtime secrets require Functions scope.
- A value in `netlify.toml` is not a secure runtime secret and is not automatically available to Functions.
- Repository `.env` files are not a production secret store.
- Changing a Function variable requires a new deploy to capture the value.

Audit names and metadata with commands such as:

```bash
pnpm exec netlify env:list --scope builds --context production
pnpm exec netlify env:list --scope builds --context deploy-preview
pnpm exec netlify build --context production
```

Do not redirect environment listings into files during an audit.

## Routing

- Publish the complete `dist/public`; Waku client navigation may depend on generated RSC payloads.
- Do not add a generic SPA fallback to `/index.html` for Waku file-based routing.
- With a catch-all Function, preserve `preferStatic: true` so CDN files win.
- Verify direct navigation, refresh, client navigation, dynamic routes, API routes, and `/RSC/` requests.
- Remove legacy Vercel or duplicate Netlify endpoint trees only after tracing every consumer.

## Headers and CSP

Recommended baseline headers depend on app behavior:

- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- HSTS only when HTTPS and subdomain implications are understood.
- `frame-ancestors` in CSP, with `X-Frame-Options` as legacy defense where useful.
- A least-privilege `Permissions-Policy`.
- Cross-origin isolation headers only when required and tested with auth popups or embedded resources.

Waku SSR/hydration can emit inline scripts. A static CSP nonce in `netlify.toml` is useless. If inline scripts are present, use a per-response nonce Edge Function that:

1. Generates a cryptographically random nonce.
2. Calls `context.next()`.
3. Changes only HTML responses.
4. Adds the nonce to CSP and the matching inline script/style tags.
5. Preserves status, response headers, and body semantics.
6. Avoids broad `unsafe-inline` for scripts.

For Convex, derive `connect-src` from the actual deployment URL and auth provider, not copied Firebase origins. Test CSP in preview and production browser consoles.

## Caching

- Hashed assets: `public, max-age=31536000, immutable`.
- HTML and mutable manifests/service workers: revalidate or no-cache according to update behavior.
- Never apply immutable caching to `/*`.
- Verify a new deployment does not serve an old HTML shell referencing removed assets.

## Post-deploy smoke test

1. Load production URL in a clean browser session.
2. Refresh every critical direct route.
3. Navigate client-side and check RSC requests.
4. Sign in and sign out.
5. Run a real Convex read and an authorized write.
6. Confirm an unauthorized cross-user operation fails.
7. Inspect response security headers and CSP console.
8. Inspect Netlify Function and Convex logs without exposing data.
9. Verify assets and HTML caching.
10. Check the deployed commit and site/deployment identifiers.
